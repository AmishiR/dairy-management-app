## Architecture

This is a **staff/admin-only** web app for a produce-to-order dairy supplier. There is no customer-facing UI here — customers will use a separate future mobile app against the same Supabase project. `project_context.md` is the authoritative deep-dive on the business rules, database, and decision history; read its §1 before touching anything involving stock, order cutoffs, pricing, or payments.

### No API layer

Supabase's PostgREST + Row Level Security **is** the API and authorization layer. There are no `app/api/*` route handlers and no client data-fetching libraries (React Query/SWR). The data flow is:

- **Reads** — Server Components call `createClient()` from `app/lib/supabase/server.ts` and query directly; RLS scopes the rows automatically.
- **Writes** — Server Actions in `actions.ts` files (`'use server'`) call `supabase.from(...).insert()` / `.update()` or `supabase.rpc(...)` for the atomic Postgres functions.
- Client components (`'use client'`) use `app/lib/supabase/client.ts` and are reserved for genuinely browser-only transient state (e.g. `app/set-password/page.tsx`).

`app/page.tsx` is a leftover Supabase connection smoke-test, not a real screen.

### Data tables

Row-listing tables use TanStack Table v8 (`@tanstack/react-table`, pinned to `^8` — v9 has an incompatible API) via the shared client component `app/components/DataTable.tsx` (click-to-sort headers, a global text filter shown once there are >8 rows, pagination past 25). Each page keeps a colocated `'use client'` wrapper (e.g. `CustomersTable.tsx`, `ProductsTable.tsx`) that holds the `ColumnDef[]` — including cell renderers for badges, links, and inline Server Action `<form>`s — and the server `page.tsx` fetches the data, flattens nested Supabase joins into plain row objects, and passes them in. `app/components/StatusBadge.tsx` is the shared active/inactive pill. Form-entry grids (`production/batches/new`, `receipts/new`) and small key/value summary tables are deliberately left as plain HTML.

### The four Supabase clients (`app/lib/supabase/`)

| File | Use from | Notes |
|---|---|---|
| `client.ts` | `'use client'` components | anon key, browser session |
| `server.ts` | Server Components, Server Actions, layouts | anon key, reads cookies |
| `middleware.ts` | `middleware.ts` at repo root only | refreshes session + does role routing |
| `admin.ts` | `'use server'` action files only | **service role, bypasses RLS — never import into client-bundled code** |

### Auth & routing (three roles: `customer` | `staff` | `admin`)

`profiles.role` is 1:1 with `auth.users`. Root `middleware.ts` → `updateSession()` runs on every request: refreshes the session, signs out and bounces any `customer`, keeps `staff` out of `/admin/**`, and sends authenticated staff/admin landing on a login page to `/staff`.

The dashboard is **unified**: staff and admin share every page under `/staff/**`. Admin's only extra is the `/admin/staff` "Add Staff" page, rendered via the `extraNavLinks` prop on the shared `AppShell`. Actually-protected admin routes live in `app/admin/(protected)/` (a route group) so that `app/admin/login/` sits outside the admin layout's auth check — an earlier structure where the layout wrapped `/admin/login` caused an infinite redirect loop.

> Note: `project_context.md` §4 still describes a separate admin dashboard; the code has since been unified per the comments in `app/lib/supabase/middleware.ts` and `app/staff/layout.tsx`.

### Security pattern for new staff/admin-only actions

Middleware and layouts are defense-in-depth, **not** sufficient on their own — a Server Action is its own reachable endpoint. Every privileged action must independently re-fetch the caller's `profiles.role` and refuse otherwise. `inviteStaff()` in `app/admin/(protected)/staff/actions.ts` is the reference implementation.

### Server Action conventions

- On validation/DB error: `redirect(\`/some/path?error=${encodeURIComponent(message)}\`)` — the page reads `error`/`success` from `searchParams`.
- On success: `revalidatePath(...)` for each affected route, then `redirect(...)`.
- Record the acting user via `created_by: user?.id` where the table tracks it (customer prices do; internal costs are a known gap).

### Pricing/cost tables and atomic RPCs

`customer_prices` and `internal_costs` are period-versioned with `EXCLUDE USING gist` constraints that forbid overlapping date ranges, so historical orders never re-price. Actions must **close the prior open period** (set `effective_to` to the day before the new `effective_from`) before inserting the new row — see `setCustomerPrice()`. Any new price/cost-like table should follow the same pattern.

Production and receipts go through atomic Postgres functions called via `.rpc()` — e.g. `create_production_batch` (generates batch no., looks up as-of-date costs, deducts raw stock, adds finished stock, computes cost, all-or-nothing) and `record_raw_material_receipt`. Do not reimplement their logic in TypeScript.

### Dispatch → deliveries

Deliveries are created **only** through Dispatch (`/staff/dispatch`), never by hand. The flow: pick an open order → `app/staff/dispatch/[orderId]/DispatchForm.tsx` (client) shows each undelivered line and → `confirmDispatch` calls the `confirm_dispatch()` RPC. Each line is one of two modes:

- **batch** (`product.is_raw_material === false`) — manufactured finished good. The form lists the product's production batches oldest-first, pre-fills an allocation, and staff can edit it; the per-batch amounts must sum to the dispatch quantity. Writes `dispatch_allocations` rows.
- **direct** (`product.is_raw_material === true`) — resold raw material (cow milk, buffalo milk, dahi). No batch picker; staff just enter a quantity, validated against `inventory_balances.current_stock`. No `dispatch_allocations` rows — the `delivery_items` insert alone deducts stock via the trigger.

Stock deduction is **not** done by the RPC. Inserting `delivery_items` fires the existing `fn_apply_delivery_item()` trigger, which bumps `order_items.quantity_delivered`, writes the `'delivered'` `inventory_transactions` row (→ `fn_apply_inventory_balance()` decrements product-level `inventory_balances`), and rolls `orders.status` to `partially_delivered`/`delivered`. `confirm_dispatch()` only adds `dispatch_allocations` rows (which batch fed which delivery line) and validates each batch isn't over-allocated. Per-batch remaining stock is derived in the app as `production_batches.quantity_produced − Σ dispatch_allocations.quantity` (no DB view). The migration is `app/supabse/migrations/dispatch.sql`; run it in the SQL Editor (it ends with `notify pgrst, 'reload schema'` so the new table/function show up over the API immediately).
